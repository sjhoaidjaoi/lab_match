## 1. 总体结论

本轮把三件不同性质的能力合并进一套契约：**名额双计数**（`quota_used` + `quota_reserved`）、**待确认收敛为统一中心**（`pending_type` + `confirm-center`）、**归档与只读**（`round_snapshot` + `locked`）。合并的结果是：**索引层与表结构先动了，执行层没跟上**。

三个结构性断点：

1. **`quota_reserved` 是死字段。** 全库 12 处出现里，8 处只在 `WHERE quota_used + quota_reserved < quota` 里做无意义改写，2 处是同一句"教师接受调剂时 +1"的文字描述，**没有任何接口或场景执行 `reserved + 1`**；而 BR-P7-11 又明令"内部调剂不引入教师二次接受与学生征求"，把这个字段唯一的生产者从规则层面删掉了。于是 INV-17、EX-25、EX-27、AC-43 四条规则同时悬空（编号 1、2、3）。
2. **`pending_type` 没有任何赋值点，且枚举不完备。** 五种 `source_type` 里，递补明确产生待确认却没有对应 `pending_type`；`pending_type = 2 补录确认` 在"补录每轮只填 1 志愿 → 单 offer 恒自动确认"的规则组合下**不可达**；三处赋值点（批处理签发、抢录拨付、内部调剂分配）文档里一个都没写（编号 7、8、9）。
3. **抢录与兜底两条新增写路径的并发依据是错的。** `admission` 唯一键含 `mentor_id`，两个不同导师抢同一学生根本不冲突，02 §6 声称的"唯一键 + 条件更新双重兜底"挡不住双录取；DDL 里没有 round+student 维度的任何唯一约束（编号 13、14）。

归档与锁定这一组是**时序自锁**：快照生成接口本身是写接口，`locked = 1` 后"所有写接口返回 400005"，若锁定按 02 §11 落在"最后一轮结束"，最后一轮的最终归档快照永远写不进去；解锁只有规则没有接口、主体"系统管理员"在 `user_type` 枚举里不存在（编号 21、22、23）。

**统计：P0 ×7、P1 ×18、P2 ×7，共 32 条。**

## 5. 本轮三个问题的直接答案

1. **`quota_reserved` 的每一处 +1 / -1（Q1）**：全库 12 处出现中，读侧 8 处均为 `WHERE quota_used + quota_reserved < quota` 形式的改写（03 §3.3 约束句、03 §5 不超录行、02 §6 超录行、全局flow §4.3、拟录取 flow L35 / L83 / L248、统筹调剂 flow L72 / L86）；写侧仅 2 处文字描述（02 §6 与 03 §5 同一段"教师接受调剂 +1、学生确认 -1 / +1、拒绝或逾期 -1"）；规则侧 3 处（INV-17、AC-43、EX-25 / EX-27）。结论：**既不是"加了没减"，也不是"used 与 reserved 重复计数"，而是根本没有加**——该列恒为 0，全部约束与验收悬空（编号 1、2、3）。
2. **四类事件的 reserved 释放路径（Q2）**：学生放弃 / 拒绝——描述存在但 3.42 无实现分支；教师被禁用——全库无规则；轮次结束——无清零任务；批次锁定——被"写接口一律拒绝"永久冻住，且因 reserved 无法减而卡死对账。0 / 4 有落点（编号 3）。
3. **对账公式（Q3）**：现式不成立。应改为 `SUM(quota) = SUM(status IN (2,3)) + SUM(quota_reserved) + SUM(quota - quota_used - quota_reserved)`，并增加闭合前提"本轮不存在 `status = 1` 记录"，否则编号 13、14、19 与 BR-P5-12 产生的跨窗待确认会让等式永不成立（编号 4）。
