# 学生实训室进组选拔平台 · 项目执行方案

> 依据《学生实训室进组选拔流程》图（8 个环节：集中宣讲 → 实训室开放日 → 意向填报 → 导师初选与面试考核 → 拟录取与学生确认 → 分轮补录 → 统筹调剂录取 → 结果公示与正式入组）编制。
> 版本：V1.0　编制日期：2026-11-09

---

## 一、可行性结论：行，但有 4 个必须先想清楚的问题

这套流程本质上是"**平行志愿 + 双向选择 + 分轮录取 + 统筹调剂**"的撮合系统，和高考志愿/考研调剂的逻辑同构，技术上有成熟范式，**做平台完全可行，而且几乎必须做**——因为核心流程被压缩在 5 天（11月2日—11月6日）内，人工用 Excel 跑"多offer确认→放弃→递补→补录→调剂"链条，出错率极高。

但以下 4 点决定项目成败，建议在动工前先定下来：

### 1. 四端建议做成"两端四角色"，而不是四个独立应用
- **学生端**：独立入口（H5 或微信小程序），学生在手机上完成填报、确认、查看结果。
- **管理端**：一个 Web 后台，内置三种角色视图——实训室教师（面试评分、拟定名单）、实训室组长（名额管理、名单审定、室内容调剂）、学院总负责（全程监控、跨室调剂、公示发布）。
- 理由：三个管理角色操作的是**同一份数据、同一条流程**，做成一个系统的三种权限，开发量大约省 40%，且不存在多端数据同步的一致性问题。若坚持四个独立前端，需额外预算 2–3 周工期。

### 2. 录取规则必须先写成"无歧义算法说明"，这是最大风险点
图里有几处规则需要学院先给出明确口径，否则开发只能猜：
- 平行志愿"不分先后"，导师看到的是全部填报自己的学生，还是按某种排序？超名额报名时是纯面试打分排序，还是导师自主圈定？
- 一个学生被多个导师同时拟录取时，导师端能否看到"该生还有其他意向"？
- 递补触发后，递补学生的确认时限是多少（沿用当前轮次窗口，还是单独给 2 小时）？
- 调剂的三个优先级（实训室内 → 全院跨室 → 未服从调剂学生谈话安置）中，前两级是否需要学生再次确认，还是直接划拨？
- **建议在需求阶段产出一页《录取与调剂规则判定表》，用 10–15 个具体案例把规则钉死。**

### 3. 时间窗极紧，"通知触达"和"自动化"是平台的核心价值
- 拟录取确认窗口只有 4 小时（11月4日 08:00–12:00），逾期未确认视为放弃并触发递补——如果学生没及时看到通知，必然产生纠纷。因此**通知体系（站内信 + 短信/企业微信/公众号模板消息 + 截止前提醒）不是可选项，是一期必须项**。
- 所有阶段的开启/关闭、自动确认、放弃判定、递补触发都应由系统按配置的时间参数自动执行，不依赖人工值守。

### 4. 图中的日期（10月28日—11月6日）已成为历史/当届时间
方案按"**全部时间节点可配置**"设计：宣讲日、开放日、各轮填报/面试/确认/调剂/公示的起止时间均做成后台参数。下届复用时只需改配置，不改代码。

## 三、系统流程与状态机设计

### 3.1 阶段机（平台总控，由时间参数驱动）

```
S0 数据准备（导入名册/实训室/导师/名额，配置时间表）
 → S1 宣讲期（信息发布）
 → S2 开放日（可附预约/签到，可选）
 → S3 意向填报（窗口控制，截止锁定）
 → S4 面试考核（名单生成→评分→名单审定）
 → S5 拟录取确认（自动确认/多选确认/超时放弃→递补）
 → S6 补录轮 R2 → S7 补录轮 R3（S6/S7 复用 S3–S5 逻辑，仅范围=剩余名额+未录取学生）
 → S8 统筹调剂（三级优先级依序执行）
 → S9 公示（1 天，异议通道）
 → S10 归档（正式入组名单锁定导出，流程关闭）
```

每个阶段有"未开始 / 进行中 / 已结束"三态，由后台时间参数自动切换；学院端保留"提前截止/延长窗口"的手动应急开关（留痕）。

### 3.2 学生侧状态机（核心）

```
未填报 → 已填报 → 待面试 → 面试完成
  ├─ 收到 1 个拟录取 → 【自动确认】→ 已录取
  ├─ 收到 ≥2 个拟录取 → 待选择 → 择一确认 → 已录取（其余 offer 自动释放→触发对应递补）
  ├─ 逾期未确认 → 已放弃（释放全部 offer → 依次触发递补）
  ├─ 无 offer 且递补中 → 递补等待 → 被递补 → 待选择（短时限）
  ├─ 本轮落选 → 补录填报（R2/R3，状态机复用）
  ├─ 服从调剂 → 调剂池 → 已调剂录取
  └─ 未服从/未安置 → 谈话安置（线下登记，线上标记）/ 未录取
```

### 3.3 名额侧约束（防超发，技术要点）

- 任一时刻"已确认录取数 ≤ 名额数"，确认操作走**数据库事务 + 名额行锁**，杜绝并发超录。
- 一名学生最终只能有一条"已录取"记录（唯一约束），确认成功即自动释放其全部其他 offer 和意向。
- 递补按名单顺位串行触发；被递补学生的确认时限单独配置（默认 2 小时）。
- 所有状态变更写审计日志（谁、何时、原状态→新状态、触发原因）。

## 四、功能模块清单（按端）

### 4.1 学生端（H5 / 微信小程序）
**一期必须（MVP）**
1. 登录认证（对接学校统一身份认证，或学号+初始密码导入）
2. 首页：流程时间轴（当前阶段高亮 + 倒计时）、我的状态卡、待办提醒
3. 实训室与导师浏览：方向介绍、名额、培养安排、考核要求（对应宣讲内容线上化）
4. 意向填报：≤3 个平行志愿（不分先后）、两个服从调剂开关、截止前可改、截止后锁定
5. 面试通知与安排查看
6. 拟录取确认：单 offer 展示自动确认结果；多 offer 择一；显式放弃按钮；倒计时
7. 补录轮：剩余名额列表 + 重新填报
8. 结果查看、公示查看、异议提交
9. 消息中心（站内信）+ 外部推送（短信/公众号/企业微信，至少打通一种）

**二期增强**：开放日预约签到、面试排队叫号、历年数据、AI+PBL 项目成果展示。

### 4.2 管理端（Web，三角色）
**实训室教师**
- 本室报名学生列表（含其平行志愿与成绩信息，权限内可见）
- 面试安排与评分表（学习态度/逻辑思维/编程基础/时间投入四维，可配权重）
- 草拟三类名单：拟录取（≤名额）、递补（有序）、内部调剂候选；提交组长审定

**实训室组长**
- 本室名额总控、导师名额分配
- 名单审定与锁定（审定后教师不可改）
- 递补顺位管理、室内调剂操作
- 本室进度看板（报名/面试/录取/缺口）

**学院总负责**
- 基础数据：学生名册批量导入、实训室/导师/名额维护、时间表配置
- 全流程总看板：各环节进度、缺口预警、放弃/递补流水
- 补录轮次发布（剩余名额池）
- 统筹调剂操作台：调剂池列表，按三级优先级批量划拨，生成安置记录
- 公示发布（名单快照 + 公示期计时）、异议受理与处理记录
- 审计日志查询、全流程数据导出（Excel）、归档

## 五、数据模型概览（核心实体）

| 实体 | 关键字段 |
|---|---|
| Student / Teacher / User | 学号工号、姓名、角色、联系方式、认证信息 |
| Lab（实训室） | 名称、方向、组长、简介、开放日安排 |
| Mentor（导师） | 所属实训室、方向、培养安排、考核要求 |
| Quota（名额） | 导师/实训室 × 轮次 × 名额数、已用数 |
| Intent（意向） | 学生 × 导师、轮次、服从调剂标志×2、提交时间 |
| Interview（面试） | 评分四维、评语、面试官、时间 |
| Offer（拟录取） | 学生 × 导师、轮次、状态（待确认/已确认/已释放/已过期）、时限 |
| WaitlistEntry（递补） | 顺位、状态、触发记录 |
| AdjustmentRecord（调剂） | 优先级级别、来源/去向、操作人 |
| Publicity（公示）/ Objection（异议） | 名单快照、公示期、异议内容与处理结论 |
| StageConfig（阶段配置） | 10 个阶段的起止时间、确认时限等全部参数 |
| Notification / AuditLog | 推送记录、操作审计 |

## 六、非功能需求

- **并发**：按学院规模估算（假设 500–2000 名学生），峰值出现在填报开启、确认开启两个整点，设计目标 300 QPS、核心接口 P95 < 500ms，常规 Web 架构即可满足。
- **可用性**：窗口期内可用性 ≥ 99.9%；确认/递补等核心链路需有数据库备份与快速恢复预案。
- **安全与隐私**：面试评分仅授权角色可见；学生成绩等敏感信息按角色脱敏；传输加密；操作全审计。
- **可配置**：所有时间节点、名额、规则开关（如递补确认时限、offer 数量上限）后台可配。

## 七、技术方案建议

| 层 | 推荐 | 说明 |
|---|---|---|
| 学生端 | 微信小程序 或 响应式 H5（Vue3/React） | 学院学生覆盖率优先，建议 H5 起步（免审核、上线快） |
| 管理端 | Vue3/React + Ant Design / Element Plus | 一个后台 + RBAC 三角色 |
| 后端 | Java Spring Boot 或 Node.js（NestJS） | 团队熟悉者优先；核心是事务与状态机 |
| 数据库 | MySQL/PostgreSQL + Redis（倒计时、窗口状态、幂等锁） | — |
| 通知 | 站内信 + 短信网关 或 企业微信/公众号模板消息 | 至少一种外部触达通道 |
| 部署 | 校内服务器 / 学院云主机，Docker 部署，Nginx + HTTPS | 数据不出校，满足管理要求 |

## 八、项目计划（参考工期 7 周，可按人力压缩/拉长）

| 阶段 | 周期 | 产出 |
|---|---|---|
| P1 需求确认 | 第 1 周 | PRD、《录取与调剂规则判定表》（关键！）、原型草图 |
| P2 设计 | 第 2 周 | UI 稿、接口与数据库设计、状态机评审 |
| P3 开发 | 第 3–5 周 | 学生端 + 管理端功能完成，阶段机与通知链路打通 |
| P4 联调测试 | 第 6 周 | 功能/并发/安全测试，规则判定表全案例通过 |
| P5 沙盘演练 + 上线 | 第 7 周 | **用模拟数据全流程彩排 2 遍**（含放弃、递补、调剂、异议场景），应急预案定稿，灰度上线 |

参考人力：产品/项目 1 人（可兼）、UI 1 人、后端 2 人、前端 1–2 人、测试 1 人（可兼）。

### 里程碑验收点
- M1：规则判定表由学院签字确认（需求冻结）
- M2：状态机 + 名额事务的单元测试全绿
- M3：沙盘演练零阻断性缺陷
- M4：正式跑完一届流程并归档

## 九、风险清单与应对

| 风险 | 等级 | 应对 |
|---|---|---|
| 录取/调剂规则口径模糊，开发返工 | 高 | M1 前完成规则判定表并签字冻结 |
| 学生逾期未看到通知引发纠纷 | 高 | 双通道通知 + 截止前 30 分钟强提醒 + 公示操作留痕 |
| 窗口期内系统故障 | 高 | 提前压测；应急预案：窗口顺延开关 + Excel 兜底模板 + 数据可导出恢复 |
| 四端独立开发导致工期超支 | 中 | 采纳"两端四角色"方案；或分端排优先级，教师/组长视图先行合并 |
| 名册/名额数据导入错误 | 中 | 导入校验 + 预览确认 + 试运行用真实名册空跑 |
| 范围蔓延（中途加考核、加日常管理） | 中 | 一期只做到"正式入组"为止，AI+PBL 过程管理列入二期 |
